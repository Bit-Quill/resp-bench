# Go Client Benchmarks — Full Details

Performance benchmarking of Go client libraries against RESP-compatible servers,
using the resp-bench Go engine.

> **Note**: Graphs are generated by CI once benchmark runs are published. Until
> then, this document describes the engine, drivers, and workload. See
> [../go/README.md](../go/README.md) for engine internals.

## Drivers Tested

| Driver | Package | Status |
|--------|---------|--------|
| `go-redis` | [github.com/redis/go-redis/v9](https://github.com/redis/go-redis) | Implemented (RESP3, retries disabled, one socket per connection) |
| `valkey-glide-go` | Valkey GLIDE Go client | Stub — client library wiring pending |

The `recording` driver is used for server-free CI tests and is not part of the
performance comparison. `go-redis` is a working driver; `valkey-glide-go` is a
stub that fails loudly on connect until its client library is wired in (see
[../go/README.md](../go/README.md#wiring-a-real-driver)); it never silently
reports success.

## Engine Notes

- **Language/runtime**: Go 1.22+.
- **Concurrency**: one goroutine per connection. Each goroutine owns one client
  connection and keeps a single request in flight — matching the
  "one in-flight request per connection" model used by the Java, Ruby, C#, Node,
  and PHP engines so results are comparable. For request-based phases the budget
  is a single shared atomic counter claimed one request at a time, so a slow
  goroutine never leaves the target unmet.
- **Metrics**: HdrHistogram range `(1, 600_000_000, 3)`; per-goroutine histograms
  are merged losslessly and emitted as Java-compatible V2 compressed base64
  payloads. The inflated V2 payload is byte-for-byte identical to the PHP
  engine's for the same samples.
- **Rate limiting**: leaky-bucket, with phase-level `rps_limit` split across
  active workers (a limit below the connection count activates only `rps_limit`
  workers rather than flooring each to 1, which would overshoot).

## Prerequisites for live runs

- Go 1.22+ toolchain (`go` on `PATH`).
- The chosen client library added to `go/go.mod` and wired into its driver stub.

## Running

```bash
make server-standalone-start
make go-run \
  DRIVER=configs/drivers/example-valkey-glide-go-standalone.json \
  WORKLOAD=configs/workloads/reference/basic-standalone-single-client-1M-reqs.json \
  SERVER=localhost:6379 \
  METRICS_OUTPUT=output/go.ndjson
```

Or through the matrix orchestrator (the `valkey-glide-go` and `go-redis` driver
ids map to the `go` engine):

```bash
python scripts/run_benchmark_matrix.py \
  --matrix configs/matrices/<your-matrix>.json \
  --output-dir results/go-run \
  --server-host localhost
```

## Workload Configuration

Go runs use the same reference workloads as the other engines (see
`configs/workloads/reference/`), so cross-language comparisons are apples-to-apples:
- 1M requests per steady phase
- 1M keys, 16-byte keys, `bench:` prefix
- 512-byte SET values
- GET/SET mix via uniform-random key selection
- No rate limiting for max-throughput runs
